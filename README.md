# 跳帮修改器（Jump Space Trainer）

通过 [Frida](https://frida.re) 连接**正在运行**的 Jump Space（Unity 6 / IL2CPP），在游戏里直接执行操作：改货币、加物品、解锁蓝图和舰船、无敌 / 锁血 / 无限弹药 / 移动速度 / 跳跃力度。
全部名称取自游戏自己的中文本地化，界面是一个独立的应用窗口。

> 非官方工具，与游戏开发商无关。仅用于你自己的单人游戏或自己的房间。所有改动只作用于**本机角色和本机存档**，不会碰其他联机玩家。

## 快速开始

> **拿到的是打包版（`跳帮修改器.zip`）？** 解压到任意文件夹（放在需要管理员权限的位置也行，日志和备份会自动改放到 %LOCALAPPDATA%），启动游戏，双击 **`跳帮修改器.exe`** 就行，
> 不需要安装 Python 或 Node。下面第 1 步和 `.bat` 文件只有从源码运行时才需要。

1. 第一次使用（源码版）：双击 **`安装依赖.bat`**（需要已安装 Python 3.10+ 和 Node.js，只用跑一次）。
2. 启动 Jump Space，进入大厅或飞船。
3. 双击 **`启动修改器.bat`**。会自动连接游戏并打开修改器窗口。
4. 用完直接关窗口：所有“锁定类”开关自动关闭并还原。**后台会继续静静待命，直到游戏退出，然后自己结束**（这是有意的，原因见“稳定性”）；
   下次再双击就能直接接上。游戏正在运行时不要强行结束后台进程。

先开修改器、后开游戏也可以：它会显示“等待游戏启动”，游戏起来后自动注入（游戏启动 30 秒后）。游戏重启也会自动重新连接。
遇到问题用 **`启动修改器(调试).bat`**（后台会另开一个控制台窗口显示日志）；日志也写在 `trainer.log` 和 `daemon.log`。

### 哪些是“临时”的，哪些会写进存档

- **物品、锁定类功能（无敌 / 锁血 / 弹药 / 速度 …）**：只改运行中的游戏，不碰存档；关掉修改器就还原。
- **货币、经验、制作配方、舰船**：通过游戏自己的接口修改并请求游戏保存，属于存档里的永久改动。
  每次改动前会自动备份 `persistent_user_data.bin`（见下）。重启游戏后的持久化尚未逐项验证，建议先看备份。

## 安全设计

- **自动备份**：第一次改存档类数据前、之后至多每 10 分钟，把 Steam 的存档复制到 `backups\时间_auto\`，保留最近 30 份。
- **可撤销**：货币、飞船物质、配方解锁、加入发现历史的装备、存入蓝图槽的蓝图都会进“操作记录”并能一键撤销（货币按差值撤销，不会覆盖你之后的其它改动；蓝图只在你没有升级过它时才会被移除，发现历史里的装备只在还没被保存成蓝图时才会被移除）。舰船解锁无法撤销，所以点之前会弹确认。
- **解锁要克制**：配方批量解锁有确认，一次最多 30 个。解锁会改变游戏进度，请只解锁需要的。
- **读回校验**：每次写入后都会从游戏读回，数值会被限制在游戏允许的范围内，失败会明确报错而不是假装成功。
- **只听本机**：网页服务只绑定 `127.0.0.1`，每次启动生成一次性令牌，校验 Host，限制 CSP；只开放固定的一组操作，不能执行任意脚本。
- **锁定类功能自动收尾**：关闭修改器窗口时，所有开关都会关闭并恢复游戏原值（速度 / 跳跃用叠加覆盖实现，移除即还原）。万一后台被强行结束，下次连接时会清掉残留的覆盖。

## 命令行（进阶）

`jsc.py` 直接调用后台的接口，适合脚本化或排错：

```powershell
.\venv\Scripts\python.exe .\jsc.py status                       # 连接、角色、血量、开关、弹药、物质
.\venv\Scripts\python.exe .\jsc.py progression                  # 货币（含 guid）、经验、飞船物质
.\venv\Scripts\python.exe .\jsc.py addCurrency <guid> 1000      # 增减货币（受上下限保护）
.\venv\Scripts\python.exe .\jsc.py levelUp 1
.\venv\Scripts\python.exe .\jsc.py cheats                       # 开关列表
.\venv\Scripts\python.exe .\jsc.py setCheat god true
.\venv\Scripts\python.exe .\jsc.py setCheat speed true 2        # 带倍率的开关：名字 开关 倍率
.\venv\Scripts\python.exe .\jsc.py setCheatParam speed 3        # 运行中改倍率
.\venv\Scripts\python.exe .\jsc.py itemList                     # 全部物品（含中文名、分类）
.\venv\Scripts\python.exe .\jsc.py players                      # 房间里的角色及 network:ID
.\venv\Scripts\python.exe .\jsc.py spawn Pickupable_MedStim 2 backpack local reject
.\venv\Scripts\python.exe .\jsc.py spawn Pickupable_Scrap_Small 1 ground local
.\venv\Scripts\python.exe .\jsc.py recipes                      # 制作配方
.\venv\Scripts\python.exe .\jsc.py ships                        # 舰船设计
.\venv\Scripts\python.exe .\jsc.py dispose                      # 关闭所有开关并释放句柄
```

`spawn <道具> <数量> <backpack|ground> <network:ID|local> [reject|ground]`：背包空位不足时默认整批拒绝，也可让多余的刷到地上；
每个道具对象占一个背包空位，不自动合并堆叠；倒地、没有背包、重物不兼容等情况会给出原因。
结果只统计已确认的数量，`uncertain=true` 表示有操作未确认，请先在游戏里看一眼再决定是否重试。`previewSpawn` 参数相同，只检查不生成。

其余旧命令（`inv`、`items`、`catalog`、`fullCatalog`、`blueprints`、`previewUnlockBlueprint`、`unlockShip`、`addBlueprint`、`give` …）保持可用；
访问 Unity 对象的脚本用 `evalMain '@文件.js'` 执行，纯元数据查询用 `evalFree`。

## 开发与测试

```powershell
npm test                 # agent 的单元测试（模拟游戏对象，不需要游戏）
npm run test:py          # 后台 / 启动器 / 网页服务 / 打包的测试：撤销、历史、白名单、安全头、服务生命周期、路径
node --check agent.js
```

需要真实游戏的试验脚本在 `snippets\`（会启动 / 关闭游戏，仅开发用）：`quit_trials.py`（反复“启动游戏 → 接入 → 关闭游戏”，统计崩溃）、
`attach_trials.py`（反复接入 / 断开，用来复现“断开后退出游戏会崩”）、`bare_detach_trial.py`（最小复现）、`crash_probe.js` + `read_crashprobe.py`（崩溃取证）。

- **热重载默认关闭**。开发时先停掉后台服务，再用 `python daemon.py` 手动启动（或设环境变量 `JUMPSPACE_WATCH=1`），它会监视 `agent.js` 和 `agent\*.js`，
  保存后自动重新注入；但重新注入 = 断开重连，**会让当前这局游戏退出时崩溃**（见“稳定性”），开发完请重启游戏。一键启动器的后台服务从不这样做。
- 改了 `webui.py` 或 `ui\` 需要重启网页服务（`ui\` 只是静态文件，刷新页面即可）。
- 游戏的 Unity 操作必须在主线程执行：agent 钩住 `PlayerLoopRunner.RunCore`，把任务排到游戏自己的帧循环里；游戏暂停或卡住时，请求可能超时。
  这个方法每秒会被调用三千多次，所以钩子本身是一小段原生代码（CModule），只有“有任务排队”或“定时器到点”时才回调 JS；原生模块建不起来时自动退回纯 JS 钩子。
- Frida 的 QuickJS 里全局 `Infinity` 是 `NaN`，代码里用 `Number.MAX_SAFE_INTEGER` 表示“永不”。

### 打包

双击 **`打包.bat`**（或 `venv\Scripts\python.exe build_app.py`），约 15 秒，得到：

- `dist\跳帮修改器\`：整个程序（约 160 MB，其中 135 MB 是 Frida 本身），入口是里面的 `跳帮修改器.exe`；
- `dist\跳帮修改器.zip`：同一个文件夹压缩后（约 60 MB），发给别人即可。

**自动打包**：推送 `v*` 标签（如 `git tag v0.1.0 && git push origin v0.1.0`）后，GitHub Actions 会跑完测试、打包，
建一个附带 `JumpSpace-Trainer-<版本>-win-x64.zip` 的**草稿** Release，检查说明后在 GitHub 上手动发布。
在 Actions 页面手动运行“打包发布”只打包、不建 Release，压缩包在该次运行的构建产物里。

做了什么：

1. 先把 agent（`agent.js`、`agent\*.js` 连同 frida-il2cpp-bridge）编译成一个文件 `build\agent.bundle.js`，所以打包后的程序**不需要 Node，也不需要 `node_modules`**。
2. 用 PyInstaller（来自创建 venv 的那份系统 Python，不用另外下载）把 `app.py`、`ui\` 和上面的 bundle 打成无控制台窗口的 exe。

入口与行为：

- `跳帮修改器.exe` 不带参数 = 打开修改器窗口（需要时自己拉起后台服务）；后台服务就是同一个 exe 加 `--service`，不用 Python。
- 带命令词（`跳帮修改器.exe status` 之类）= 命令行工具，输出要在终端里运行才看得到；开发时也可以用环境变量 `JUMPSPACE_HOME=<打包版文件夹>` 让 `jsc.py` 连到打包版的后台。
- 日志、操作历史、存档备份、`daemon.key` 都放在 exe 旁边（该文件夹不可写时放到 `%LOCALAPPDATA%\JumpSpaceTrainer`），所以**发布前别把自己运行过的文件夹打包**——
  `打包.bat` 每次都重新生成 `dist`，里面不会带这些。
- 界面窗口用系统自带的 Microsoft Edge（`--app` 模式）；没有 Edge 时退回默认浏览器。
- exe 没有数字签名：Windows Defender / SmartScreen 对“会往别的进程注入的未签名程序”可能提示或拦截，必要时手动放行；这和源码版是同一回事。

### 实现要点

- **制作配方**：解锁的是配方 `m_CraftableObject` 指向的装备或部件的 GUID，不是配方文件自己的 GUID；成功与否以游戏的“已解锁制作列表”为准。
- **为什么解锁了还不能制作**：配方分两类（看它的分类 `CraftableCategory.m_CategoryEntryKind`）。
  消耗品、弹药、工具（`Craftable`）解锁后直接出现在制作台。武器和飞船部件（`Blueprint`）不是：制作台只列出**蓝图槽里存着的蓝图**（一件具体的、带模块的装备）。
  “解锁”只是让游戏认识这个型号，不会生成蓝图（游戏里的蓝图来自扫描台，只有初始的默认解锁才会自带一份：`PlayerDataDefaults.EnsureDefaultBlueprintsForUnlocksAsync`）。
- **蓝图和配方互相独立**：游戏允许给**没解锁配方**的型号保存蓝图（`CanScanItem` 不看解锁状态），制作台也会列出这样的蓝图。所以修改器把它们拆成独立的操作：
  “解锁配方”只改解锁标记；“加入发现历史”和“存入蓝图槽”只管蓝图，不碰配方。做法和游戏扫描时一样：
  1. `ItemGenerator.Generate(模板, 难度, 随机数, 品质)` 让游戏自己生成一件该品质的装备，再按编辑器里的设置改写它的词条和等级（见下面的“自定义词条”）；
  2. `AddToBlueprintHistory` 把它记进**发现历史**（游戏只允许保存“找到过”的东西的蓝图，`WasFoundLocally` 查的就是这份历史；历史最多 50 条，满了挤掉最早的）。
     游戏的扫描台和“我的蓝图”页的“保存为蓝图”都读这份历史——“加入发现历史”只做到这一步，保存留给你；
  3. “存入蓝图槽”再接着 `CanScanItem` → `TrySetBlueprintInSlot(物品, 分类, 空槽位)`：游戏把它存进槽位、从历史里移除并保存存档；修改器再读回槽位确认。
  每次都生成一件新的装备，同一型号可以有很多份蓝图。任何一步失败都会撤回本次加进历史的记录并如实报错；分类没有空槽位时“存入蓝图槽”会提示“蓝图槽已满”（加入发现历史不受影响；槽位满了需要先在游戏里销毁一个旧蓝图或购买扩容）。
  决策逻辑在 `agent/blueprint_flow.js`（有单元测试），和游戏对象打交道的适配层在 `agent/gear.js`。
- **蓝图的品质**：`ItemGenerator.Generate` 的第四个参数是 `Nullable<ItemRarity>`（指定品质）。修改器在原生内存里按 .NET 的布局造这个结构（`hasValue` + 品质值），游戏就会生成该品质的装备；
  逐个型号核对过（48 个型号 × 4 个品质）：游戏给的品质都和要求的一致。品质决定词条位数和等级上限（`EffectiveMaxLevel`，例如武器 5 / 7 / 10 / 12 级）。
- **自定义词条**（编辑器）：一件装备能装哪些词条，由它的模板决定——模板自带的“基础词条”任何品质都能装，各流派的“专属词条”只能在自己的品质范围里装。规则是从游戏数据读出来的，并用游戏自己生成的近 200 件装备核对过（全部符合）：
  词条品质不能高于装备品质；同一个词条只能装一次；词条等级 1–该词条在该品质的上限；蓝图等级要付得起所有词条升级（等级 − 1 ≥ 各词条升级点数之和），也不能超过游戏对这件装备算出的上限
  （上限由装备品质和词条品质共同决定，所以“全部拉满”先把词条品质提到最高、让游戏重新算上限，再分配升级点数）；每个词条按品质有若干个 0–1 的数值，“最高”取 1。
  编辑时每改一下，`gearEdit`（物品页是 `itemEdit`）就让游戏在内存里造一件（不记录、不写存档），词条文字用游戏自己的 `GetLocalizedDescription`，所以看到的数字就是游戏里会显示的；
  点“加入发现历史 / 存入蓝图槽”才由 `makeBlueprint` 真正记录：用生成器造一件该品质的装备，再改写它的词条（GUID / 品质 / 数值 / 等级）和 `m_Level`，然后走上面的“发现历史 → 蓝图槽”流程。规则在 `agent/gear_spec.js`（有单元测试）。
- **舰船**：设置解锁标记后调用 `HandleUnlockedNewSpaceshipBlueprint`，再等“已拥有舰船列表”确认。
- **货币 / 经验**：通过 `MetaProgressionManager` 的静态接口读写，并合并请求 `SaveDataToCloud`。
- **移动速度 / 跳跃**：游戏的移动数值是 `ComposableProperty<float>` 优先级栈（基础值在 0，游戏自己的修正在 1–4）。
  修改器在栈顶加一条以“设置对象自身”为发起者的覆盖（优先级 10），关闭时只移除这一条。
- **物品**：服务端创建持久道具再拾取到指定槽位，或走地面掉落流程；不会替换已占用的槽位。

### 稳定性

**核心结论：不能从运行中的游戏上断开 Frida。** 2026-10-10 的调试里，游戏在退出时崩溃或卡死了很多次，最后用一个最小实验定位了原因：
只做“接入 → 空脚本（没有任何钩子）→ 断开”，之后再关闭游戏就会崩（故障模块是已经卸载的 `frida-agent.dll`，位置是 Gum 钩子入口函数的开头）。
也就是说 Frida 断开后会在游戏里留下指向自己（已卸载）的残留钩子，游戏退出时一调用就出事。反过来，**接入一次、一直不断开**，直到游戏退出，则每次都能正常退出。

所以现在的设计围绕这一点：

- **后台是常驻服务**（`daemon.py --service`）：独立于界面窗口，单实例（命名互斥量），每个游戏进程只接入一次，一直持有这一个连接直到游戏退出，
  然后自己结束（没有游戏、也没人在看窗口 90 秒后退出）。关闭窗口只会关开关，不会断开。
  游戏运行时“彻底退出后台”会被拒绝并提示原因；强行结束后台进程等同于断开，会让这局游戏退出时崩溃。
- 一个游戏进程只注入一次：不热重载、不重复接入；游戏启动 30 秒后才注入。
- 钩子本身是原生代码（CModule），每次被调用都直接从内存读取游戏的 `ApplicationQuitCoordinator.m_QuitInProgress`，
  **游戏一开始退出就不再回调 JS**；若退出被取消，后台检测到游戏还活着，会自动恢复。
- 实测（Windows 11 24H2 + Frida 17.23.1，游戏用 Steam 的 `-force-d3d11` 启动）：这样的构造下连续 **17 次**“接入 → 关闭游戏”全部正常退出
  （约 2.7 秒），包括“窗口开关 3 次后再退出游戏”；而在“接入过又断开过”的游戏上，退出必崩或卡死。
  这是针对已定位原因的结构性规避，**不保证 Frida 本身没有别的问题**。
- 如果游戏意外退出，后台会在 `daemon.log` 里写 `[exit-report]`：最后几次调用，以及 Windows 崩溃事件里的故障模块和偏移，方便判断是不是修改器引起的。
- 建议：游戏完全进入主菜单之后再开修改器（先开修改器也行）。

### 游戏更新之后

物品、装备、词条、分类和中文名都是每次启动时从游戏自己的资源目录读出来的，游戏新加的武器会自动出现，不用改修改器。
内部类名 / 方法名可能变化。出现问题时界面会提示具体错误（例如 `GAME_API_CHANGED`），不会静默失败。
用 `jsc.py describe <类名>` 或 `snippets\` 里的脚本重新确认字段，再改 `agent\` 里对应模块；测试里有对应的模拟对象可参考。
