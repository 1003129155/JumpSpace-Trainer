# snippets — 开发调试工具

摸索游戏内部结构、排查崩溃时用的脚本，**不是修改器的一部分**，日常使用不需要它们。
除 `ui_mock.py` 外都要求游戏和后台服务已经在运行。

## 界面

- `ui_mock.py`：不连游戏，用写死的数据起一个界面服务（蓝图页的各种状态：槽位已满、发现历史…），打印网址并写入 `out\dev_url.txt`，用浏览器看界面。
  它的操作记录写在临时文件里，不会混进真正的记录，也不会备份存档。货币页和角色强化页在这里是空的。

## 不重启游戏试当前源码

注入游戏的脚本不会热更新，改了 `agent\` 要重启游戏才生效。下面两个工具把**当前源码**直接拿到运行中的游戏里跑：

- `live_unlocks.py`：跑 `agent/gear.js`、`unlocks.js`、`items.js`、`blueprint_flow.js`、`gear_spec.js`。
  `read`（只读：装备列表、槽位、发现历史）、`gear <型号key> <品质0-3>`（只读：编辑器看到的词条、等级上限、“拉满”的结果）、
  `consistency [种子数]`（只读：规则和游戏自己生成的装备是否一致）、`roundtrip <型号key>`（**会写存档**，做完会撤回，运行前确认制作台没打开）、
  `rpc <方法> <JSON参数…>`（像修改器那样调用一个 RPC，如 `gearEdit`、`makeBlueprint`，打印返回值）。
- `live_spawn.py <测试脚本>`：跑 `agent.js` 里刷物品的那一段，测试脚本在 `spawn_tests\`（**会往游戏里刷东西**）。

## 只读的查看工具

- `calls_of.py <方法名片段>`：反汇编游戏里的某个方法，列出它调用了哪些方法（名字来自 `out\Assembly-CSharp.txt`，泛型 / 内部函数用游戏的元数据补名字）。
  用来弄清“游戏自己是怎么做这件事的”。看得出结构，看不出条件，不是反编译器。
- `read_save.py <存档文件>`：把存档（KSRB 头 + LZ4 压缩的 MessagePack）解成 JSON。先复制一份再解，别直接对正在写的文件操作。
- `probe_item_attrs.py`：哪些可刷出的物品带属性（品质、词条、等级）。
- `probe_slot_counts.py`：生成器给每个型号、每个品质多少个词条位（多个随机种子统计）。

## 会启动 / 关闭游戏的试验脚本

这些脚本通过 Steam 启动游戏、用 `CloseMainWindow` 关闭（相当于点窗口的 X），再查 Windows 的崩溃事件，用来验证“退出游戏会不会崩”：

| 脚本 | 做什么 |
| --- | --- |
| `quit_trials.py N [--uptime S]` | 后台服务在运行时，重复“启动游戏 → 自动接入 → 关闭游戏”，统计崩溃次数 |
| `attach_trials.py N [--close \| --close-detached]` | 反复接入 / 断开 Frida，再关闭游戏。**断开过的游戏退出时会崩或卡死**——这是修改器从不断开的原因 |
| `bare_detach_trial.py` | 最小复现：接入 → 空脚本 → 断开 → 关闭游戏 |
| `crash_probe.js` + `read_crashprobe.py` | 往游戏里装异常记录器（寄存器、回溯），事后把地址解析成 模块+偏移；用法见 `crash_probe.js` 开头 |
| `exp_noop_hook.js` | 实验：只在 `RunCore` 上挂一个不执行任何 JS 的空原生钩子（用来排除“钩子本身”） |

跑 `attach_trials.py` / `bare_detach_trial.py` 之前要先停掉后台服务（界面里“关于 → 彻底退出后台”，或让它空闲 90 秒自己结束）；
这两个脚本会故意把游戏弄成“断开过”的状态，之后请重启游戏。

JS 脚本用 `jsc.py` 执行：访问 Unity 对象的用 `evalMain '@文件.js'`，纯元数据查询用 `evalFree`。

## 一个坑：游戏的移动数值是“按优先级叠加的覆盖栈”

实验时不要用玩家对象当发起者去清除覆盖，否则会把游戏自带的基础条目一起删掉。
修改器里的 `agent/movement.js` 用设置对象自己做发起者，关闭时能精确还原。
